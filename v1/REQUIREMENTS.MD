# Inovix Design System - Generator Prompt

Purpose: generate a UX-only design system, maintained as Markdown files, that the devs' AI coding agents read and implement so every Inovix frontend looks and behaves the same.

Devs start their AI prompt with: "Follow this design system: " then point it at the local design system directory path. That is all. The AI reads the directory, infers every component, state, token, behavior and page the requirement implies, and applies the whole system without the dev naming anything. In that mode the AI MUST IGNORE REQUIREMENTS.MD (rule 26): REQUIREMENTS.MD is the generator build spec, not part of the design system.

Consumers start at README.md (rule 29). Three modes exist (rule 26 and rule 27): CONSUMER (default, ignores this file), GENERATOR (builds the files from this file), AUDIT (reads this file, checks the generated files, edits nothing until approved).

## Hard rules

1. Output ONLY Markdown files (.md). ZERO code. No React, no Vue, no Angular, no HTML, no CSS, no SCSS, no JS, no TS, no JSON, no snippets of implementation, ever.
2. Everything is UX specification: prose, tables, ASCII diagrams, token references only.
3. No emojis anywhere. No em dashes. No en dashes. Use plain ASCII hyphens and plain wording.
4. Every visual value must be configurable via variables. All colors, spacing, radii, fonts, shadows, z-index, breakpoints, motion timings live in ONE source of truth documented as `theme-variables` (the generated project uses `theme-variables.scss`, but this design system documents the tokens, not the code). White-label rebrand = swap one token file, regenerate. Components must reference tokens, never hardcoded values. State this rule explicitly in every component file.
5. Default = light. Document both themes' token values.
6. Icons: best free professional icon set only (Lucide). Document the full icon usage policy: naming, sizing, stroke width, spacing, when to use icon vs text, icon-only buttons need aria-label + tooltip.
7. Skeletal loaders (skeleton screens) are MANDATORY for every data-driven component. Every component doc must include a skeleton spec: shapes, shimmer, duration, layout per breakpoint.
8. Light + dark themes via a single theme toggle
9. Holy Grail Layout: fixed header, fixed left sidebar (collapsible), fluid main content, footer. NO right sidebar. Full fluidity: clamp() + grid, no fixed widths, everything scales.
10. Header: navy blue (#03182D), top left, in EVERY app, the INOVIX logo. The logo is TEXT ONLY, always: never an image, never an icon, never a graphic mark, no SVG/PNG/JPG/WebP logo file anywhere. It is styled text per the source logo spec ("INOVIX-Logo-Blueprint-and-Specifications", 29 October 2026; that file is STALE on dark backgrounds, superseded by this rule). Exact text, 3 lines: line 1 wordmark "INOVIX", line 2 descriptor "SOFTWARE LABS", line 3 tagline "Engineering Intelligence. Securing the Future.". Typeface: DejaVu Sans Regular (400) for all three lines. Units are construction units "u", not pixels or millimeters; scale all geometry and strokes together (wordmark 100 u nominal, outline 1.1 u, descriptor 15 u, tagline 12 u; wordmark glyph advance 13 u after previous glyph ink width; layout width 336.56 u; baselines: wordmark 0 u, descriptor -34 u, tagline -63 u; descriptor custom-spaced to match wordmark width; tagline normal spacing, centered by visible ink bounds). Colors: exactly two, white #FFFFFF and navy #03182D (source alpha 252/255 = 98.82%, solid preferred). Dark background = navy blue. Combo rule: on navy (header, dark theme, navy panels) ALL logo text is white; on light or white surfaces ALL logo text is navy. The swap is a token decision tied to theme + surface, never a per-page guess. The source PDF's two letter-split variants (white INOVI + navy X, or navy INOVI + white X, navy outlines, navy descriptor/tagline) are transparent-bg print-style lockups that FAIL on a solid navy header, so they are superseded: no two-tone letter split, no navy outline, no navy descriptor or tagline on any navy surface.

26. Three modes, hard separation. GENERATOR mode: ONLY when the design system owner (the person who created this design system) explicitly asks to build, implement, regenerate or extend the design system inside this folder. In generator mode the AI parses and follows this REQUIREMENTS.MD and produces the component MD files listed under Directory structure. REQUIREMENTS.MD is the generator build spec, nothing else, never a component or token spec. CONSUMER mode (the default): when a dev says "Follow this design system:", "use this design system", "design system:", "apply this design system", or any equivalent, and points the AI at this design system directory path (local, online, git, or any other path where the component MD files live). In consumer mode the AI MUST IGNORE REQUIREMENTS.MD completely: never read, parse, quote, follow or cite it, never treat it as a component, token or behavior spec. The AI starts at README.md (the consumer entry point) and uses ONLY the generated design system MD files (README.md, theme-variables.md, brand/, layout/, navigation/, forms/, data-display/, feedback/, overlays/, media/, pages/, micro-interactions/, a11y/, i18n/, theming/, qa/, ai-prompts/, docs/). If the generated files do not cover something the dev asks for, infer from the component files and tokens, never from REQUIREMENTS.MD. If one prompt mixes both, consumer mode wins for app work; generator work needs its own explicit request. REQUIREMENTS.MD is generator-only and is not part of the design system consumers consume. AUDIT mode is the third mode, defined in rule 27: it reads REQUIREMENTS.MD like generator mode but changes nothing until the owner approves.
27. Audit mode (read-only). Trigger: the design system owner says "audit this directory", "audit the design system", "check if the design system is generated", "verify the design system", "verify if my design system is taken care of", or any equivalent. The words audit, check or verify from the owner make it audit mode, never consumer mode, even though the phrase "design system" appears. In audit mode the AI MUST read REQUIREMENTS.MD as the spec and compare it against the generated files in this folder. Never edit, create or delete any file until the owner approves the report. Do not skim or sample: check every file. Order of work:
    a. List every path in the Directory structure section and report which are missing, empty or stubs. Expand the wildcard entries (`data-display/chart-*.md`, `data-display/graph-*.md`, `data-display/map-*.md`) into the concrete files they imply from rule 20 and report which are missing.
    b. Run a script kept OUTSIDE the design system folder (never add it to the folder) that checks every .md file for: em dashes, en dashes, emojis, code fences, hardcoded hex, px and ms values outside theme-variables.md, and mentions of REQUIREMENTS.MD. Report counts per file. Fixed constants defined by the spec itself (#03182D, #FFFFFF, the 44px minimum touch target, the 8px scale, the 4.5:1 contrast ratio) are allowed where they define or document a token or a rule.
    c. Check every component file for all 17 template sections and the full state matrix. List files with missing sections or missing states.
    d. Verify brand/ against rules 10 and 25 line by line: text only, exact 3 lines, DejaVu Sans Regular 400, construction units, two colors only, white on navy and navy on light, no two-tone split, no navy outline, aria-label, 44x44 target, provisional tokens flagged "pending brand approval". Confirm brand/ is fully self-contained and does not depend on REQUIREMENTS.MD.
    e. Check that token names used in component files exist in theme-variables.md, and that both light and dark values plus the white-label override section are documented.
    f. List new files the spec implies but the Directory structure does not cover, for example app contexts (rule 21), micro components (rule 22), chart, graph and map types (rule 20), and the long app-context and action list in Deliverables.
    g. Check the premium criteria of rule 28: navy tonal ramp anchored on #03182D, tinted neutrals, single interactive accent, contrast table per theme x surface x state, glass and shadow fallbacks, focus ring tokens, theme parity, and the Premium treatment note in every component file. Report gaps and propose edits or new files.
    h. Output a report grouped by severity (blocker, major, minor) with file paths, a short fix recommendation per finding, and a list of proposed new files. Then wait for the owner's approval before changing anything.
28. Premium look and feel (applies to every file; audited in rule 27 step g). Direction: white and navy, executed as a restrained, high-end enterprise look. Navy #03182D stays the anchor brand color (header, logo surface, dark theme base) and white #FFFFFF stays the anchor light surface. Rule 10 is untouched: the logo itself stays exactly two colors.
    a. One hue family. Define a tonal navy ramp of about 11 steps (50 to 950) in OKLCH, sharing the hue of #03182D, with #03182D documented as a named step of that ramp, not an unrelated value. Neutrals (backgrounds, borders, muted text) are tinted slightly toward the navy hue, never pure gray, never pure black. Light theme: white and near-white tinted surfaces, navy text. Dark theme: layered navy surfaces (base darker than raised surfaces), off-white text, never pure white on pure black, never a simple inversion of the light theme.
    b. One interactive accent. Primary actions, links, focus rings, selection and active navigation use a single accent taken from the navy ramp (a brighter, more chromatic step of the same hue family), with exact light and dark tokens. No second brand hue. Semantic colors (success, warning, error, info) are muted and harmonized with the navy family and always paired with an icon and text, never color alone. Chart series colors follow the same discipline: ordered, color-blind safe, navy-led, with defined light and dark palettes.
    c. Restraint. Accent area stays small: at most one primary-filled action per view region. Large surfaces stay calm (white, tinted neutral, or layered navy). Gradients are subtle, same-hue and low contrast, used only for glass overlays and brand moments, never behind text or dense data. Shadows are soft, layered and navy-tinted, never pure black. Glass = blur + 1px hairline highlight border + subtle inner light edge, never lowering text contrast below AA, falling back to a solid token surface under forced-colors, high contrast and reduced transparency.
    d. Typography and rhythm. Clear type scale with generous line-height and tracking tokens, tabular numerals for data, one UI family plus one optional display family, strict 8px rhythm, generous whitespace, consistent alignment. Density modes (comfortable, compact) are tokens.
    e. Motion. Calm and fast: short, eased, purposeful, no bounce on enterprise surfaces, prefer opacity and elevation changes over large movement, everything removed or reduced under prefers-reduced-motion.
    f. Accessibility is part of premium. Text contrast target WCAG AAA 7:1 for body text where feasible, AA 4.5:1 minimum everywhere, UI components and focus indicators 3:1 minimum, verified per theme x surface x state and recorded in a contrast table (theming/color-palette.md and a11y/contrast.md). A visible focus ring token with offset on every interactive element in both themes. 44px touch targets. Support high contrast, forced colors, reduced transparency, reduced motion and color-blind safe states.
    g. Polish details. Consistent radius scale, optical alignment of icons and text (Lucide stroke weight tokens matched to type weight), crisp hairline borders, thoughtful empty states, calm precise microcopy (no exclamation marks, no emojis), skeletons that match the final layout exactly with zero layout shift.
    h. Theme parity. Light and dark are equally polished. The theme toggle is smooth (no flash on load), respects the OS preference on first visit, and persists the choice.
    i. Every component file states a short "Premium treatment" note inside its Do / Do not list (template section 11) explaining how it applies this rule. This adds no new template section.
    j. No exceptions by component. Premium applies equally to buttons, inputs, selects, checkboxes, switches, cards, tables, lists, tabs, menus, tooltips, modals, drawers, toasts, badges, avatars, charts, maps, skeletons, empty and error states, pages (404, 403, 500, maintenance), print output and every micro component. Each component defines: calm resting state, refined hover (subtle tint or elevation shift, never a jarring color jump), tactile pressed state, clear focus ring, graceful disabled state, and a loading state that matches the final layout. Control heights, padding, radii, border weights and icon sizes come from one shared scale so components feel like one family. No component may look default, unstyled or visually louder than its importance.
    k. Premium carries into the regeneration prompts. Every Prompt snippet (template section 17) and every ai-prompts template restates the premium essentials in a line or two (navy ramp, tinted neutrals, single accent, restraint, AA minimum contrast, calm motion, theme parity) so components regenerated in any framework keep the same look and feel.
29. Consumer entry point and concrete values (fixes apps that come out ugly). a. Root README.md, AGENTS.md and CLAUDE.md (identical short pointer to README.md, so agents that auto-load them find the entry point) are mandatory. README.md is: consumer rules, reading order (tokens, brand, layout, then only the needed components), what a correct app looks like, and recipes for common requests (form page, info modal, menu entry), plus a pre-answer quality bar. It states that the zero-code rule applies to the design system files only, and that the app built from it is real code in the requested format. It tells consumers not to open REQUIREMENTS.MD or .git. b. theme-variables.md gives every color as OKLCH AND an sRGB hex fallback, generated by script, with contrast ratios computed by script, never estimated. c. One hue family: the navy ramp hue is the hue of #03182D (OKLCH hue 250). Step 950 is exactly #03182D. The ramp is defined once, theme-independent. d. The header is navy with white text in both themes, never a raised or white surface. In dark theme the primary fill is a bright ramp step, never navy on navy. e. The UI font must be loadable: document a CDN source with pinned version for every face, and never use a face that is not installed on typical devices as the UI family (DejaVu Sans is logo only). f. Layout files carry a "Build notes (authoritative)" section with measurable layout rules and a wireframe, placed before the state matrix. g. Header height must fit the logo lockup; descriptor and tagline use a minimum font size floor.
